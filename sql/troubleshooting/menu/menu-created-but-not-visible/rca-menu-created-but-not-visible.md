# RCA: Menu created in the database but not visible

| | |
| --- | --- |
| **Status** | Four root-cause candidates identified and confirmed against the actual code paths (stored procedures + `RoleManagement.aspx.cs`). Not yet reproduced against one specific live menu/tenant — recurs in PROD per report, but no concrete `MenuId`/`Employerid` was in hand at the time of writing. |
| **Affected objects** | `sp_GetDynamicMenuItems.sql`, `sp_GetDynamicMenuHierarchy.sql`, `sp_InsertDynamicMenuHierarchy.sql`, `tMenuDetails`, `TMenuHierarchy`, `TDynamicMenuHierarchy`, `TRolePagesMapping`, `TUSerPagesMapping` |
| **Symptom** | A menu item was created in the database, but for a given employer it does not appear — either in the "Dynamic Menu" hierarchy tab on `RoleManagement.aspx`, or on any employee's left menu at that tenant, or both. |
| **Related scripts** | `diagnose-menu-setup-by-employer.sql` (this folder) |

## Summary

"Menu visibility" for one employer actually depends on four separate tables
that all have to agree, driven by two independent code paths — the
runtime left menu and the admin hierarchy editor use *different* logic, so
a menu can be broken for one and fine for the other. Below are the four
causes, in the order `diagnose-menu-setup-by-employer.sql` checks them.

## Cause 1 — Master row missing or inactive (`tMenuDetails`)

`sp_GetDynamicMenuItems.sql:31-36` (runtime left menu) requires
`md.isactive = 1` and an exact `Employerid` match on `tMenuDetails`.
`sp_GetDynamicMenuHierarchy.sql` doesn't check this table directly (see
Cause 3), but `sp_InsertDynamicMenuHierarchy.sql:151-187` — the only
supported way to *create* a menu through the UI — always writes a
`tMenuDetails` row per `Employerid` it's run for, copying
`NavigateURL`/`PageName`/`iconname` from the `Employerid = 0` row for the
same `MenuId`.

**Effect:** if `tMenuDetails` has no row (or `ISActive = 0`) for this
`MenuId` at this `Employerid`, the menu is invisible on the runtime left
menu for **every** role and every user at that tenant — not a per-employee
issue. If the row only exists at `Employerid = 0` and was never created at
the target tenant's own `Employerid`, this is the most common way that
happens: someone added the menu to the global template but the
tenant-specific row was never generated (normally that only happens by
running the tenant through the Dynamic Menu tab's Submit action — see
Cause 3).

## Cause 2 — Hierarchy link missing (`TMenuHierarchy`)

Both `sp_GetDynamicMenuItems.sql` (lines 31, 47-53, 73-74, 105-106) and the
admin tree-rebuild in `sp_InsertDynamicMenuHierarchy.sql:129-149` depend on
a `TMenuHierarchy` row (`MenuId`, `ParentMenuId`, `Employerid`,
`parentseq`) existing at the same `Employerid` as the `tMenuDetails` row.

**Effect:** a `tMenuDetails` row with no matching `TMenuHierarchy` row at
the same `Employerid` is orphaned — it exists as master data but is never
reachable through either code path, since both join the two tables
together rather than reading `tMenuDetails` alone. The reverse is also
possible: a `TMenuHierarchy` row whose `ParentMenuId` doesn't itself have a
`tMenuDetails`/`TMenuHierarchy` row at that `Employerid` — this hides the
entire branch under that parent, not just the one node.

## Cause 3 — Dynamic Menu tab cache is stale (`TDynamicMenuHierarchy`)

This is the cause specific to the admin hierarchy editor, and the one most
likely to explain "I created it in the DB but the tab doesn't show it."

`sp_GetDynamicMenuHierarchy.sql` does **not** query `TMenuHierarchy`/
`tMenuDetails`. It returns `TDynamicMenuHierarchy.DynamicMenuXML` — a
cached XML blob — for the given `Employerid`, falling back to the
`Employerid = 0` row's blob if that tenant has zero rows of its own.
`RoleManagement.aspx.cs`'s `bindDynamicMenuTree()` (line 1670) just loads
that XML string into the tree control (`RadTreeViewDynamicMenu.LoadXml`,
line 1680) — there is no live query anywhere in this path.

The cache is only ever regenerated by `btnDynamicUpdate_Click`
(`RoleManagement.aspx.cs:1603-1640`) → `sp_InsertDynamicMenuHierarchy`,
which rebuilds `TDynamicMenuHierarchy`, `TMenuHierarchy`, and
`tMenuDetails` together from whatever nodes are currently in the tree
control at the moment Submit is clicked.

**Effect:** a menu row inserted directly into `tMenuDetails`/
`TMenuHierarchy` — by script, migration, or ad-hoc `INSERT` rather than by
adding a node in the tab's tree and clicking Submit — never touches
`TDynamicMenuHierarchy`. The row is genuinely in the database (Causes 1
and 2 can both check out clean), but the Dynamic Menu tab keeps rendering
the old cached tree and the new item is invisible there until the cache is
regenerated. Note this is *specific to the admin tab* — if Causes 1, 2, and
4 are all otherwise satisfied, the runtime left menu (which reads the
tables directly) is unaffected by a stale cache.

## Cause 4 — No role or user grant (`TRolePagesMapping` / `TUSerPagesMapping`)

Independent of all three causes above: `sp_GetDynamicMenuItems.sql`'s two
`UNION` branches (lines 70-88, 90-121) require **either** a
`TRolePagesMapping` row for the employee's `RoleID` **or** a
`TUSerPagesMapping` row for the employee's `UserID`, for this `MenuId` at
this `Employerid`.

**Effect:** even with the master row, hierarchy link, and cache all
correct, no employee sees the menu in their left menu until at least one
role or user grant exists for it at that tenant. This doesn't affect the
Dynamic Menu tab itself (which shows the raw hierarchy, not per-user
access) — it only affects whether end users ever see the item once the
admin-side setup is otherwise complete.

## How to verify

Run `diagnose-menu-setup-by-employer.sql` with `@MenuName` (or `@MenuId`)
and `@EmployerId` set. Its five result sets check, in order: name
resolution across all employers, Cause 1, Cause 2, Cause 3, and Cause 4 —
each with a `LikelyCause` column naming the specific gap found. Because the
causes are independent, more than one can apply at once (most commonly 3
and 4 together: a menu added directly to the tables with no grants yet
either).
